# Auth Flow Investigation Report — Frontend Session, Boot & CSRF

- **Date**: 2026-08-06
- **Site**: prod `expense.local` (:8000 gunicorn, `developer_mode: 1`); test `expense-test.localhost` (:8001 bench serve + vite :8081)
- **App**: `expense_manager` at `/home/korecent/frappe/my-bench/apps/expense_manager`
- **Frontend**: Vue 3 + frappe-ui v0.1.278 (Vite build)
- **Mode**: read-only. No source files were modified for this report. Findings below are traced from code only.

---

## 1. Production boot / session flow

The SPA is served by a Frappe web page (not a static host), so the server injects session state into the HTML before first paint.

1. Browser hits `http://expense.local/expense_manager/` → Frappe renders `expense_manager/www/expense_manager.py`.
2. `get_context()` builds `boot = {user: frappe.session.user, lang: frappe.local.lang}` and, **only when the user is not Guest**, `boot["csrf_token"] = frappe.sessions.get_csrf_token()` (`www/expense_manager.py:6-13`).
3. `www/expense_manager.html` serialises that context into globals via a Jinja loop:
   `window.user`, `window.lang`, and (when logged in) `window.csrf_token` (`expense_manager.html:26-30`).
   The token generation (`frappe.sessions.get_csrf_token()`) persists `csrf_token` in the session, which is what makes CSRF enforcement active for that session on subsequent requests.
4. The built bundle boots (`frontend/src/main.js`): `setConfig('resourceFetcher', frappeRequest)`.
5. `frappeRequest` (`node_modules/frappe-ui/src/utils/frappeRequest.js`) stamps every request with:
   - `X-Frappe-Site-Name: window.location.hostname`, and
   - `X-Frappe-CSRF-Token: window.csrf_token` (when present and not the literal `{{ csrf_token }}` placeholder).
   Default method is POST (`/api/method/<method>`).
6. Routing is gated on the injected global: `isAuthenticated() = window.user && window.user !== 'Guest'` (`router.js:6-8`). Guards:
   - `/` redirects to `/dashboard` when authenticated, else `/login`.
   - Any route with `meta.requiresAuth` (everything under `AppShell`) redirects to `/login` when not authenticated (`router.js:78-85`).
   - The history base is `/` in dev, `/expense_manager/` in prod (`router.js:74`).
7. Login (`pages/LoginPage.vue:49-50`): `call('login', { usr, pwd })`, then a **full page reload** to `/expense_manager` so the boot script re-runs and populates `window.user` / `window.csrf_token` before the SPA mounts. This is why no reactive auth store is needed for first paint.
8. Logout (`pages/AppShell.vue:150-156`): `call('logout')` then a full page reload to `/expense_manager/login`.

Server-side authorisation is entirely cookie-based: the Frappe `sid` session cookie is set at login and carried on every request; the SPA never sends credentials in headers.

## 2. Dev flow (vite :8081 → bench :8001)

- Vite serves `frontend/index.html`, which contains **no Frappe boot script**. `window.user`, `window.lang`, and `window.csrf_token` are all `undefined` at mount time.
- The e2e harness mirrors boot manually after logging in (`scratch/e2e_verify.js:318-341`): it POSTs `/api/method/login` through the vite proxy (setting the session cookie for `expense-test.localhost`), then runs `window.user = 'Administrator'` so the router guard lets the SPA in.
- Its `apiCall()` helper (`e2e_verify.js:216-229`) uses raw `fetch` with **no CSRF header**, and these POSTs succeed against the test bench. Reason: on the test bench the session's `csrf_token` is never generated (nothing calls `frappe.sessions.get_csrf_token()` there — boot never runs), and `frappe/auth.py:87` (`validate_csrf_token`) returns early when the session has no saved token (`not saved_token`). So CSRF is effectively not enforced in the test stack.
- In prod the boot script generates the token, so `validate_csrf_token` becomes active and the header from `frappeRequest` is mandatory.

Summary of differences:

| Aspect | Dev (vite :8081 → :8001) | Prod (expense.local :8000) |
|---|---|---|
| SPA served by | Vite dev server | Frappe `www/` page |
| Boot globals (`window.user` / `csrf_token`) | absent — harness injects `window.user` | injected by `expense_manager.html` |
| CSRF enforced | effectively no (no saved session token) | yes (token generated by boot) |
| SPA requests | `frappeRequest` via vite proxy | `frappeRequest` + `X-Frappe-CSRF-Token` |
| History base | `/` | `/expense_manager/` |
| Login reload target | `/` | `/expense_manager` |

## 3. Related gotcha found while validating (GET vs POST)

Whitelisted **GET-only** endpoints reject `call()` (which POSTs) with `PermissionError: GET method required`. The app therefore uses `request({ url, params })` and reads `res.message` for those (`list_budgets`, `get_budget_usage`, `get_balance`, `list_allowed_categories`, `get_dependent`, report summaries). This is a frontend-API contract detail, noted here because it sits next to the auth/session work.

## 4. Gaps identified

- **Stale `window.user`.** The guard only trusts the boot-time global. If the Frappe session expires (or is revoked) while the tab is open, `window.user` still reads as a real user, so the SPA keeps rendering and every API call starts 403ing with no redirect to login.
- **No reactive auth.** There is no shared store/session resource; `window.user` is read ad-hoc (`AppShell.vue:128`, `router.js:7`). Nothing reacts to session loss.
- **CSRF is implicit.** It works only because boot generates the token; any path into the SPA that skips the `www/` page (e.g., a static-hosted build) would lose both the boot globals and the token.

## 5. Options considered (no code changes made)

1. **Status quo** — boot globals + `frappeRequest`. Minimal, works in prod, zero extra requests. Retains the stale-session gap.
2. **Mount-time session liveness check (recommended if changed)** — on app mount, `call('frappe.auth.get_logged_user')`; if the returned user disagrees with `window.user` (or the call 403s), clear `window.user` and `window.location` to `/expense_manager/login`. One extra round-trip at boot, closes the stale-session gap. Optionally also map 403 `Incorrect CSRF`/session errors from `call()` to a logout redirect.
3. **Pinia auth store + session resource** — single source of truth for `user` / `csrf_token`; components subscribe instead of reading `window.user`. Cleanest long-term shape, most churn (all pages that read `window.user`).
4. **frappe-ui `Auth` plugin / session store** — the idiomatic frappe-ui answer, but **not exported by frappe-ui v0.1.278** (`node_modules/frappe-ui/src/index.ts` has no `Auth`/`session`), so it would require upgrading frappe-ui or vendoring it. Not viable without a dependency bump.
5. **Route-level re-validation** — guard each `requiresAuth` navigation with `get_logged_user`. Most robust, but adds a network round-trip on every navigation and complicates the boot-time redirect flow.

**Recommendation:** keep the current boot-based approach (option 1) and, if session-robustness matters, add option 2's mount-time liveness check — smallest change that removes the stale-session gap without upgrading frappe-ui.
